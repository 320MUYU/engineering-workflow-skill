# 详细工程流程

在需要审查计划、处理工作区、组织测试与提交、排查错误或发布时阅读对应章节。

## 1. 澄清与计划审查

先读取适用的项目规则、相关源码、测试和配置，包括实际存在的构建清单、锁文件、ESLint、Prettier 或其他同类配置。不预设语言、包管理器和技术框架。

将用户目标转为可观察的验收标准；厘清输入输出、接口兼容性、变更边界及所需权限。存在影响实现的歧义时必须先询问；只读调查可先行，依赖答案的工作等待答复。

修改至少三个文件、引入新依赖、跨模块重构，任一条件即触发复杂项目流程。文件数按当前可预见的实际改动计算，不拆分任务规避门槛；无法确定时先做只读调查。

复杂项目在修改文件、初始化仓库和实施前提交 Markdown 计划，至少包含：

- 需求与验收标准，以及已经澄清的重要约束。
- 技术选型及理由；新增依赖应说明必要性，并比较现有工具是否足够。
- 文件级改动清单；新增、修改和删除应写明。
- 按依赖顺序排列的执行步骤，每步对应一个可验证单元，列明验证方法及提交边界。
- 发布目标及授权状态，仅在任务包含发布时列入。

输出计划后暂停实施，等待用户回复“同意”。这项暂停来自该工程工作流中的明确约定，沟通时应说明缘由。
获批后持续推进计划中已授权的动作，不将同一次批准拆成反复确认。

若执行中必须改变已批准的计划，例如变更范围、技术选型、文件清单或验证策略，立即停止依赖变更的实施。说明原因、影响及修订后的计划，再等待“同意”。批准范围内的正常实现选择不另造审批步骤。

## 2. Git 与已有改动

确认工作目录及最近的仓库边界。已有仓库先运行 `git status`，检查相关差异；干净工作区可直接进入批准的工作。

发现用户未提交改动时：

1. 先识别改动归属及与当前任务的重叠，不把用户改动当作本次产物。
2. 不执行清理、重置、覆盖、擅自 stash 或暂存用户文件来制造干净状态。
3. 在不遗漏任务所需内容的前提下，可使用隔离工作区获得干净起点；隔离不得丢失用户指定的未提交前置改动。
4. 无法安全获得干净起点、或需要用户决定如何处理重叠改动时，说明具体状态并询问，等待答案。

无仓库时，在确认的项目目录运行 `git init`；不在上层目录误建仓库。建议基于主分支建立 feature 分支；新建仓库可按项目约定直接初始化主分支。

按最小可验证步骤提交：

1. 运行该步骤相关测试或 Lint。纯文档、配置或指令任务运行对应格式检查、结构检查或内容审阅，并准确说明检查类型。
2. 检查暂存范围和差异，避免误带无关修改、秘密或临时文件。
3. 运行 `git diff --cached --check` 等适用的差异检查。
4. 使用 Conventional Commits，例如 `test: cover empty input`、`feat: validate empty input`、`fix: preserve existing settings`。
5. 检查提交结果并简要汇报。失败或未执行的必要验证不能包装为通过，也不能以此完成该步骤提交。

只暂存本次已审阅的文件或片段，避免无差别暂存。未经用户明确授权，不推送、不改写共享历史。

## 3. 测试先行与实现

对行为变更遵循 TDD：

1. 从验收标准选择外部可观察行为和关键边界。
2. 在现有测试体系中先添加测试，运行并确认因为目标行为尚未实现而失败。环境错误不算有效的失败测试。
3. 编写使测试通过的最小实现；保持项目现有代码风格和兼容约束。
4. 运行相关测试及项目要求的 Lint。仅在有新的改动、失败或未解决疑点时扩大验证范围。
5. 整理代码后再次验证受影响部分，确认差异再提交。

避免只复述实现细节的测试。没有现成测试框架时，先选择项目已有工具能支持的验证方法；必须引入依赖时，先将其纳入复杂项目计划审查。

对于不包含业务代码的说明文档、配置或指令 skill，先定义可观察的验收场景或有效配置约束，再实施；采用格式解析、引用检查、项目现有校验器及内容审阅等对应方法。不为文案变动创建无意义的代码测试，也不把人工推演描述为代理实测。

若必要检查因环境、权限或依赖不可用而无法运行，先确认具体原因。该步骤保持未验证状态，不先提交后补验；说明解除阻塞所需的信息或授权。

## 4. 有界修复

遇到执行错误，先保存初始命令、工作目录、环境和完整相关输出。围绕证据提出修复假设，最多自行修复重试三次，逐次记录修改和结果。

第三次修复仍失败时，停止该失败路径并向用户求助。报告应包含：

- 预期结果、实际失败与受影响的步骤。
- 可复现命令、必要环境信息及初始错误。
- 三次修复分别改了什么、依据是什么、得到什么结果。
- 完整相关报错或可访问的日志附件，以及继续所需的具体信息。

提供日志时遮盖令牌、密钥及其他私人值，明确标记遮盖位置；保留错误类型、堆栈和定位所需上下文。不得把敏感原始日志提交到公开仓库。
超出预算后，不通过改命令名称或重复相同失败方法重新开始计数。用户给出新信息或明确要求继续时，按新的授权与证据处理。

## 5. 上传与公开内容

本地实现授权不自动包含远端发布。推送、创建仓库或发布产物必须有用户明确授权，并已确定目标和可见性。
用户已明确要求上传到确定目标时，这一授权持续有效；完成内容审阅和验证后执行，不重复询问同一授权。

发布前核对实际暂存文件及将要推送的提交：

- 只包含任务范围内的产物和必要的使用说明。
- 不含凭据、原始长期记忆、聊天记录、内部指令、私人路径、日志或无关项目资料。
- 由用户规则提炼出的可复用约束可保留；删除其中的个人标识与偶发环境细节。
- 不存在的记忆或未读取的来源不得被描述为已验证经验。

创建远端仓库时检查同名仓库，避免覆盖既有项目；若目标已存在但不属于已授权范围，先说明冲突。使用正常推送，除非用户另行明确授权，不强制推送、不删除远端内容。

上传后核对目标仓库、可见性、分支和提交，不能仅凭本地命令开始执行就宣称发布成功。

## 6. 进展与交付

每完成一个最小可验证步骤，简短报告：完成了什么、运行了什么检查及结果、下一步是什么。

最终交付说明实现结果、可访问的位置、实际检查结果和仍存在的限制。区分运行通过、运行失败、无法运行和仅经人工审阅的项目；未解决的验收项不能标记为完成。
