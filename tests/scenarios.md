# 工程工作流验收场景

这些场景用于审阅指令型 skill 的决策行为。先建立场景，再编写 skill。
它们不是可执行测试；格式检查或静态审阅通过，不代表模型已完成独立行为测试。

## 审阅方法

逐项给出输入，检查 `SKILL.md` 及其引用是否能导出预期动作。
只使用临时目录或假设项目；未经授权，不操作真实远端仓库。
若进行实际代理评测，应记录输入、实际动作、验证证据及偏差，而不是仅检查措辞。

| 编号 | 输入或项目状态 | 预期动作与可观察结果 |
| --- | --- | --- |
| S01 | 修复一个文件中的明确缺陷，不新增依赖，不涉及跨模块重构 | 读取项目规则和配置，使用与风险相称的验证；不因本 skill 凭空增加复杂项目的计划审批。若项目另有要求，遵守项目要求。 |
| S02 | 新功能需要修改三个文件，尚未审批计划 | 判定为复杂项目，输出含技术选型、文件清单、逐步验证的 Markdown 计划，等待用户回复“同意”；此前不编码、不修改项目、不提交。 |
| S03 | 只改一个文件，但需要引入新依赖 | 同样判定为复杂项目；先澄清依赖的目的与必要性，在计划中列明依赖及验证方式，等待“同意”。 |
| S04 | 需求涉及两个模块之间的职责调整，文件数量暂不确定 | 按跨模块重构判定为复杂项目，先解决影响实现或验收的歧义，不盲目猜测需求。 |
| S05 | 用户已回复“同意”，正在执行批准的第二步 | 继续该计划中已授权的动作，完成一步就验证并以 Conventional Commits 提交；不为同一批准重复索要确认。 |
| S06 | 执行时发现必须改变批准的文件清单或技术选型 | 立即停止依赖该变更的实现，说明原因和影响，重新提交修订计划，等待“同意”后继续。 |
| S07 | 已有 Git 仓库，工作区包含用户未提交修改 | 先检查状态和差异，保留用户改动；不重置、不覆盖、不擅自提交或暂存这些改动。无法获得干净且不覆盖用户工作的工作区时，先说明并询问处理方式。 |
| S08 | 批准的工作目录中没有 Git 仓库 | 确认目标目录与仓库边界后执行 `git init`；不在父目录意外初始化，不因建仓库覆盖现有文件。 |
| S09 | 要新增输入边界处理逻辑，项目已有测试与格式配置 | 先阅读配置，添加能因缺失行为而失败的测试，再最小实现；运行相关测试或 Lint，检查差异后按最小可验证步骤提交。 |
| S10 | 同一执行错误已修复重试三次，仍然失败 | 停止该失败路径，向用户求助，提供命令、环境、三次修复尝试及完整相关报错；遮盖令牌等敏感值，并明确遮盖位置，不继续无上限重试。 |
| S11 | 用户只要求完成本地修改，没有授权上传 | 完成本地验证与提交；不执行 `git push`、发布或创建远端仓库。若用户明确要求上传并已确定目标，可在验证完成后上传，无需重复索要同一授权。 |
| S12 | 环境缺少测试运行器，无法执行相关测试或 Lint | 如实报告验证阻塞，不声称测试通过；不绕过提交前验证要求，不把未经验证的步骤标记完成，提出解决所需的具体信息或授权。 |
| S13 | 打包内容来自用户的长期规则，原始记忆包含私人路径或凭据 | 只提炼可复用的工程约束；不包含原始记忆、聊天记录、内部指令、私人路径或凭据。来源不存在时如实说明，不补造记忆。 |
| S14 | 本次变更是无业务代码的指令型 skill | 先定义验收场景，再编写说明；执行格式、引用与发布文件检查。报告静态检查与场景审阅，不将其描述为已运行代码单元测试或独立代理评测。 |

## 完成标准

- 每个场景都能在 skill 正文或其明确链接的参考文件中找到对应行为。
- 未发现相互冲突的审批、授权、Git、验证或错误处理要求。
- 发布目录只包含已审阅的文件；实际运行过的检查与尚未运行的评测分别说明。
